# Lessons

Captured lessons (per `CLAUDE.md` §0.7). Review for promotion to `CLAUDE.md` §24 when validated.

Started on 2026-10-20 for the nopCommerce 5.00 repository. Entries #1–#9 are carried over from the 4.9 repository
(its number is given as "4.9 #N") because they apply here unchanged. Entries #10 onwards were learned on 5.00. The full
4.9 history is in `tasks/lessons-4.9.md`; read it when porting a 4.9 plugin.

This file is shared. Lessons about how one developer wants to work with Claude (how changes are handed over, their own
browser session, their own folders) go in that developer's `CLAUDE.local.md` (`CLAUDE.md` §0.10).

| # | Mistake | Rule |
|---|---|---|
| 1 | *(4.9 #110)* Asked to "add the solution to the repository", the agent committed and tried to push; when the push was blocked it tried again by other routes. The user handles git. | **Prepare the repository (`.gitignore`, secret scrub, file review) and hand over the exact git commands; never commit or push, and never retry a push through another tool or the user's terminal.** |
| 2 | *(4.9 #4)* Put `#region Utilities` after the public method regions. | Region order is **Fields → Ctor → Utilities → public method regions**; helpers come before the methods that use them (`CLAUDE.md` §7). |
| 3 | *(4.9 #5, #2)* Reused a Razor helper that no longer existed in the target nop version; the build passed and the page died on first request. | **Razor compiles on first request — a clean build proves nothing about views.** Check every framework type and helper a ported view uses against the target version, then load the page. |
| 4 | *(4.9 #74)* A `.js` edit seemed to have no effect; WebOptimizer's disk cache served the old bundle across rebuilds and restarts. | **A `.js` or `.css` edit needs `Presentation/Nop.Web/wwwroot/bundles` emptied** — not a rebuild, not a restart (`CLAUDE.md` §9.11). |
| 5 | *(4.9 #73)* A `let` in bundled admin JS was moved by the minifier out from under the hoisted function that read it — a silent no-op only in the minified bundle. | Use `var` for a closure variable read by a hoisted inner function in bundled JS (`CLAUDE.md` §9.11). |
| 6 | *(4.9 #75)* A partial that bound delegated handlers to a long-lived container stacked them on every render (one confirm became four). | A partial that binds delegated handlers to an element it does not own calls `.off('.ns')` first and namespaces every handler (`CLAUDE.md` §9.12). |
| 7 | *(4.9 #77)* Measured a page that was still running a debugging probe from an earlier session. | **Reload the page before every verification round.** When live behaviour contradicts the source, first check the page runs the source — read the function back (`fn.toString()`). |
| 8 | *(4.9 #104)* Claimed what a page shows "on load" from the page after its scripts had run. | Check "on load" on the raw server response (`fetch` + parse) and the scripted page separately; a difference between the two is the finding. |
| 9 | *(4.9 #103)* Signed the admin out of the shared browser session while testing. | The browser session is the user's. Before `/logout` or any form that can sign someone in, check who is signed in; never sign the user out or change their credentials. |
| 10 | Porting the SSO plugin, admin JS read `data.success` / `data.message`; nop 5.00 admin JSON is PascalCase, so every value was `undefined` and the import, test and badge buttons silently did nothing. | **nop admin JSON is PascalCase** (`data.Success`). Check every property a ported script reads against the JSON the action actually returns (`CLAUDE.md` §10.5). **Added 2026-10-22:** more precisely, nop's Newtonsoft `DefaultContractResolver` (`ServiceCollectionExtensions.cs:331`) keeps C# names as declared — a model's properties arrive PascalCase, an anonymous `Json(new { success = false })` arrives lowercase (4.9 #23). |
| 11 | Porting the SSO plugin, packages compiled against newer `Microsoft.IdentityModel.*` than nop 5.00 ships; it built and would have failed at runtime. | **Pin plugin packages to the versions the host ships**, and pick third-party packages whose dependency floor is at or below them. "It compiles" does not prove runtime compatibility (`CLAUDE.md` §10.5). |
| 12 | A store-scope save on the SSO Configure page wrote the hidden system-wide fields as empty and 0, blanking settings the page did not show (D6, 2026-10-19). | **A form saves only what it displays.** When a page shows different cards per scope, the save path branches the same way; test a save at each scope and read the other scope's values back. |
| 13 | `sed` with `&` in the replacement text (a heading containing "&") pasted the matched line into the result and garbled four headings (2026-10-20). | Escape `&` (and `\`) in `sed` replacement text, or use the Edit tool; grep the result after any bulk `sed`. |
| 14 | During the Keycloak test the agent asked the user to set the test users' passwords and offered a reply button reading "Done: alice and bob have passwords". The user clicked it without the step having happened ("I never created alice or bob, I assumed you had done it"), and several sign-in attempts failed for no visible reason. (2026-10-21) | **A reply button never asserts that the user did something.** Phrase it as a question or a neutral "Continue", say plainly which steps are the user's and which are the agent's, and verify a precondition (here: the Credentials tab shows a password) before building on it. |
| 15 | The user signed in to Keycloak three times "in the browser pane" while the pane was hidden in the app; nothing reached the page the agent was driving, and each round looked like a server bug. | **Before asking the user to act in the browser pane, show it** (`show_pane` → `preview`, the right tab in front) and check `document.visibilityState`. When an action "did nothing", read the network log and the form fields before suspecting the server. |
| 16 | Every SAML request from the SSO plugin was refused by Keycloak (`invalid_token`). The request decoded fine locally, so the plugin and ITfoxtec were suspected first; the cause was nop's `NopRedirectResultExecutor`, which URL-decodes the whole address of any `RedirectResult` (with `SecuritySettings.AllowNonAsciiCharactersInHeaders` on), turning `%2B` back into `+`. | **A redirect whose query carries Base64 or a signature must not go through `RedirectResult` in nop** — set the `Location` header from a small `IActionResult` (see `SamlRedirectResult`). To find such a fault, compare the raw `Location` header with what the library produced, and replay the payload re-encoded. |
| 17 | The SSO plugin's helper `UnbindEither(HttpRequest, Saml2Request)` was also used for a `Saml2LogoutResponse`. In ITfoxtec `Saml2LogoutResponse : Saml2Request : Saml2Response`, so C# chose the request overload of `Unbind`, which reads `SAMLRequest` — the log-out response was never validated. Adding an overload for `Saml2Response` would not have helped (the request one stays the closer match). | **When a library has request and response overloads on related types, call the one you mean through a separately named helper** — overloads are picked by the declared type and the most-derived match. Check the type hierarchy (a reflection probe in `CW.Tests`) before trusting an overload. |
| 18 | The SSO health column and the `ManageSsoSecurity` permission were written, built, tested and checked in the browser in `C:\Work\CW_NOP_5` (the user's personal repo), while the project now lives in `C:\Work\CW_NOP_5_0`. Both repos hold the same plugin, so nothing looked wrong until the user found nothing to commit. (2026-10-22) *Since 2026-11-02 the roles are reversed: `C:\Work\CW_NOP_5` is the only working copy and `CW_NOP_5_0` is retired; the rule is unchanged.* | **Before the first edit, confirm the repo: edit only under the session's working directory, and when a path in the request or an earlier turn points at another checkout of the same code, ask which one.** Say the full path of the repo in the plan and in the closing summary. |
| 19 | Porting `CW.Common`, `HttpContextHelper` got the current action through `EngineContext.Current.Resolve<IActionContextAccessor>()`. nop 4.9 registered it; nop 5.00 does not (ASP.NET Core 10 marks it obsolete, ASPDEPR006), so the resolve returned `null` and every `IsController` / `IsAction` check answered false — no exception, no build warning. (2026-10-22) | **When porting, list every `EngineContext.Current.Resolve<T>()`, `GetService(...)` and `TryResolve` in the plugin and confirm 5.00 still registers `T`.** A service locator turns a missing registration into a silent null. Build the action context from the endpoint (`httpContext.GetEndpoint()?.Metadata.GetMetadata<ActionDescriptor>()` + `GetRouteData()`), and add each type found to `CLAUDE.md` §10.5. |
| 20 | Porting CW.Core phase 2, the first draft held `Services/EventConsumer.cs` back because it could not be constructed yet (it needs a phase-5 factory) and called it "mostly UI" after reading its constructor and the first handlers. An independent review found it also cascades packname, subsidy, product-group and customer deletes, advances packname shipments and completes exchanges, and that `StoreDeletedEventConsumer`, active in the same phase, relies on those cascades. | Before leaving an event consumer out of a phase, list **every** event it handles and every class that relies on what it does; never judge it by its name or its first handlers. nop resolves consumers itself, so one that cannot be constructed breaks every event it handles inside nop's own flows: bring its dependency forward instead of holding it back. `NopStartupTests` checks the CW side of this. |
| 21 | Porting CW.Core part 4.0, the agent read `ViewPathsRegistrar` (never called) and the expander, and wrote that the view location expander was dead code; it missed the ten default paths in `ViewsPathsRegistry`'s **static constructor**, which make every CW view at a nop view's path replace it. The user caught it when the department ACL forks were called "unreachable" (2026-10-26). | **Before calling code dead, read every member of the classes it uses — static constructors, field initialisers, defaults — and prove it with a test or a run, not by the absence of callers.** For views, check `CLAUDE.md` §10.4 and the override inventory first. |
| 22 | Porting Integration.Odoo, the plugin (which compiles against the built CW.Core DLL, §10.2 Pattern C) was installed on a site where CW.Core was not installed. nop accepted the install; on restart it could not load the Odoo assembly's types (`FileNotFoundException: Nop.Plugin.CW.Core`) and **the whole site failed to start**. 4.9 never showed it because CW.Core was always installed there. (2026-10-26) | **A plugin that references another plugin's assembly declares it in `plugin.json`: `"DependsOnSystemNames": [ "<SystemName>" ]`.** nop then refuses the install until the dependency is installed (or queued). Before installing a plugin on a test site, check its dependencies are installed (`App_Data/plugins.json`). |
| 23 | Porting Integration.Odoo, `<Nullable>annotations</Nullable>` was added to silence CS8632 warnings from a few `string?` carried over from 4.9. With nullable annotations on, ASP.NET Core MVC treats every non-nullable `string` property of a bound model as implicitly `[Required]` (nop does not set `SuppressImplicitRequiredAttributeForNonNullableReferenceTypes`), so the Configure save failed validation on fields the form never posts (`ConnectionStatus`) or posts blank by design (`ApiKey`) — a 200 with no message, nothing saved. The build and unit tests were clean. (2026-10-27) | **Do not switch on a nullable context (`enable` or `annotations`) in a plugin whose models were written without one** — remove stray `?` annotations instead. A plugin that does opt in (`CLAUDE.md` §7) declares every optional model string `string?`. When a POST returns the page with no visible error and nothing saved, check `ModelState` for implicit-required fields first. |
| 24 | Porting Integration.Odoo, admin views registered their script with `NopHtml.AddScriptParts(ResourceLocation.Footer, Url.Content("~/Plugins/…"))` (the `CLAUDE.md` §9.8 example of the time). nop 5.00's `NopHtmlHelper.GetSrcUrl` drops the first character of a local path and expects the rest to start with `/`, so the resolved `/Plugins/…` became `Plugins/…` and the page died with `ArgumentException: The path in 'value' must start with '/'` — on first request only, since views compile at runtime. (2026-10-27) | **Pass `NopHtml.Add*/Append*ScriptParts` and `*CssFileParts` the raw `"~/Plugins/…"` path, never `Url.Content(...)`.** Load every page a ported plugin owns before calling the port done (lesson #3). |
| 25 | Checking which requested Odoo fields the Integration.Odoo plugin never reads, the agent guessed each C# property name from the field name (`qty_available` → `QtyAvailable`) and reported `qty_available` unused. The variant model calls it `QuantityAvailable`, and it sets every combination's stock; dropping it would have zeroed stock on every variant. Caught before the edit, by a last grep. (2026-10-28) | **Before calling a mapped field unused, find its property through the `[JsonPropertyName("…")]` attribute (or the mapping) in every class that binds it, then search for reads of that exact property.** Never infer a property name from a JSON, column or form name. |
| 26 | Porting the CW.Standard theme, the header's hard-coded "Go to cart" was moved to a `CW.Theme.Standard` resource with a plain `@T(...)`. The theme is meant to render without that plugin (it reads the plugin's settings by key, with defaults); once the plugin was uninstalled the header showed the raw key `plugins.cw.theme.standard.headerlinks.gotocart`. Found by the uninstall check, not by the build or the page loads. (2026-10-29) | **A theme that must work without a plugin reads that plugin's resources with `GetResourceAsync(key, languageId, logIfNotFound: false, returnEmptyIfNotFound: true)` and a fallback, never a bare `@T(...)`.** Test a theme with each optional plugin uninstalled. In nop 5.00 a pending uninstall is applied by *Reload list of plugins*, not by a restart. |
